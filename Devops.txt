2. Bitbucket Access & Branching Strategy
2.1 ESB Access Groups
Bitbucket access is controlled using six ESB-specific groups:
Group Name	Permissions
ESB Integration Dev RO	Read-only
ESB Integration Dev	Write, create branches
ESB Integration Dev Admin	Admin access
ESB Integration Dev Pipeline PR	Pipeline-related PR rights
ESB Integration Dev PR	PR review/merge permissions
ESB Integration Dev PR Master	Highest PR authority (CM/DevOps/Leads)

Key Rules
•	RO users cannot push to any branch.
•	Only PR/PR Master groups can merge into protected branches.
•	Master/Main merges are limited to CM and select DevOps users.

2.2 Old Branching Strategy (Deprecated)
Branches used:
•	master
•	build
•	develop
•	feature/*
Flow
1.	Developer creates feature branch.
2.	PR → develop.
3.	Develop pipeline runs:
o	Build → MUnit → JAR → JFrog → Deployment to environments.
Challenges:
•	Multiple pipelines & branches.
•	Duplicate artifact generation.
•	High maintenance.

2.3 New Simplified Branching Strategy
Current branches:
•	main
•	release/*
•	feature/*
2.3.1 New Workflow
1.	Developer creates feature/ branch from main (via Jira).
2.	After development → PR raised to main.
3.	On merge:
o	Jenkins builds the JAR.
o	Auto deployment to Dev environment.
4.	After QA approval:
o	Create release branch (e.g., release/1.1.0).
o	Release JAR is used for QA → UAT → PreProd → Prod.
5.	After Prod:
o	Sync release changes back into main.
2.3.2 Benefits
•	Only two active branches to maintain.
•	A single artifact is deployed across all higher environments.
•	No redundant JAR creation.
•	Supports parallel releases using release branches.

3. JFrog Repository Structure
JFrog hosts artifacts per Mule runtime version.
3.1 On Prem (4.2)
•	esb-snapshot-local
•	esb-release-local
3.2 CloudHub Classic (4.4) & CloudHub 2.0 (4.6/4.9)
•	esb-cloudhub-latest-snapshot-local
•	esb-cloudhub-latest-release-local
Rules
•	Snapshot → Dev deployments.
•	Release → QA/UAT/PreProd/Prod deployments.
•	If JAR missing from Cloud repository → fallback to AWS JFrog.
•	Missing in both → deployment fails.

5. Jenkins CI/CD Pipeline Architecture
5.1 Multibranch Pipeline Setup
•	Jenkins job name must match Bitbucket repo name.
•	Detects all branches automatically.
•	Uses centralized Jenkins folder for:
o	Shared Jenkinsfiles
o	Deployment parameter JSONs
o	POM and scripts
5.2 Main Pipeline Stages
1.	SCM checkout
2.	Maven build
3.	MUnit tests → Minimum 75% coverage
4.	JAR creation & upload to JFrog
5.	Deployment to target environment
6.	Notifications (email)

5.3 POM Files per Runtime
File	Runtime	Notes

6. Deployment Architecture
6.1 Development Environment – Automatic Deployment
Triggered on main branch merge:
1.	Jenkins builds → JAR → JFrog.
2.	Token generated via Client ID/Secret.
3.	Org ID, Env ID, Target ID fetched.
4.	Deployment:
o	If app exists → PATCH
o	Else → POST
5.	Property handling:
o	Secure configuration JAR encrypts/decrypts sensitive fields.

6.2 Non-Prod & Prod Deployment – Manual
Manual due to risk & approvals.
Steps:
1.	Choose environment & market.
2.	Fetch artifact from JFrog.
3.	Deployment script executed manually.
4.	Deployment via:
o	Anypoint API + curl
o	Or Anypoint CLI (preferred for new deployments)

6.3 Artifact Naming

8. ICM Validation in Jenkins
8.1 Purpose
To ensure deployments are tied to valid Jira change requests.
8.2 Validation Steps
An ICM ticket must:
1.	Exist in Jira
2.	Have status:
o	To be processed
o	In Deployment
3.	Have application type:
o	ASB
o	MuleSoft ASB
8.3 Technical Workflow
•	Groovy script: backend validation via Jira API.
•	JavaScript: enables/disables Build button based on validation.
•	Stored in Jenkins via Simple Theme Plugin.
